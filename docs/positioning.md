# 用途と設計原則

Tasking は、同期コールバックから始める非同期処理について、誰が task を所有し、
どの要求を重複と扱い、いつキャンセルするかを呼び出し箇所で読めるようにする。
既存のアプリ構成に組み込める、外部依存のない小さなライブラリである。

## 解決する問題

Swift の `Task {}` は unstructured task を作る。呼び出し元の同期関数が戻っても
処理は続くため、task のハンドルを保持し、キャンセルと終了確認を行う所有者が必要になる。
たとえば保存ボタンでは、次の判断が必要になる。

- 保存中の再クリックを無視するか、前の保存をキャンセルするか、並行実行するか。
- 画面を閉じたらキャンセルするか、アプリ側の所有者の下で継続するか。
- キャンセル済みの保存が遅れて終了したとき、表示や結果を更新してよいか。

Tasking は所有と重複方針を管理する。最後の判断に必要な業務状態や結果の世代管理は、
ViewModel やアプリのサービスが管理する。

## 用途の選択

| 必要なスコープ・責務 | 選択 |
|---|---|
| 関数のスコープ内で並行に進めて合流する | `async let` / task group |
| View の表示期間や入力値に応じて実行する | SwiftUI `.task` / `.task(id:)` |
| 同期 UI コールバックから開始し、ハンドルを所有する | `ViewTaskStore` |
| async 関数の呼び出しを重複制御し、最終結果を受け取る | `ActionRunner` |
| 非 UI の所有者が、最新の要求で task を置き換える | `TaskingCore.TaskSlot` |

構造化並行性では子 task の終了をスコープが待ち、キャンセルを task tree に沿って伝える。
SwiftUI `.task` では View がライフサイクルを管理する。これらのスコープが処理の寿命に
合う場合は、その仕組みを使う。

たとえば `.task(id: query)` は検索語に応じたロードに向く。保存中の再クリックを
`.ignoreNew` で拒否したい同期ハンドラや、画面を閉じてもアプリの所有下で継続したい同期処理には、
`ViewTaskStore` で所有者と方針を明示できる。

## 設計原則

### 所有者と実行場所を明示する

`ViewTaskStore` と `ActionRunner` は MainActor に隔離する。`TaskSlot` は独立した actor とする。
Runner は呼び出し元の task 内で operation を実行し、Store と Slot は自分が作った task を所有する。
この区別によって、どこにキャンセル要求を出すかが決まる。

### キャンセル要求と実終了を区別する

Swift のキャンセルは協調的である。Store はキャンセルされた run を重複判定の対象から外すが、
task のハンドルは終了まで保持する。Slot も置換前の task が終了するまで保持する。
終了を確認する場面では `awaitCompletion(of:)` または `waitForIdle()` を使う。

### アプリの判断をアプリの状態として表す

lifetime はキャンセル対象を選ぶラベルであり、ライフサイクルとの接続は利用側が行う。
表示状態、業務エラーからの回復、再試行、古い結果の破棄も利用側が決める。
`CancellationContext` は、各メソッドがキャンセルに協調する責任を引数として表す。

### 少ない概念に責務を集約する

公開する所有者は Store と Slot、実行制御は Runner に限定する。内部では Action の追跡を
`ActionRuns`、task の所有を `OwnedTasks` が管理する。登録・解除の規則を集約し、
利用者と保守者が同時に理解する必要のある状態を減らす。

## 採用時に引き受けること

- Store の所有位置と、ライフサイクルごとのキャンセルを設計する。
- operation でキャンセルを確認し、必要に応じて結果や後始末に世代ガードを設ける。
- loading・進捗・結果・エラーを ViewModel の観測可能な状態として持つ。
- 順序保証、同時実行数制限、永続化、バックグラウンド実行には用途に合う仕組みを使う。
- Store / Runner の同期処理が MainActor を占有する量を、実際の workload で測る。

FIFO キューが必要ならキュー、アプリ全体の状態と副作用を統合したいならその責務を持つ
アーキテクチャが適する。Tasking の採用判断は、明示的な task 所有と重複方針が必要かで行う。

## 公開方針

このライブラリは、unstructured task の所有と方針を明示する設計のリファレンス実装でもある。
コードを読むことや、MIT ライセンスの下で自分のアプリに取り込むことを想定する。
機能の追加は、この責務配置と公開契約の小ささを保てるかで判断する。
