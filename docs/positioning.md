# 用途と設計原則

Tasking の目的は、非構造化タスクの所有と実行方針を、呼び出し箇所から読み取れるようにすることである。
外部 package への依存を持たず、アプリケーションの ViewModel やサービスに組み込んで使う。

## 扱う問題

保存ボタンのような同期コールバックは、開始した非同期処理の終了を待てない。
`Task {}` で処理を開始すると、コールバックが戻った後もタスクは続く。
そのため、次の判断をアプリケーション内のどこかに置く必要がある。

- タスクのハンドルを誰が保持し、キャンセルや終了確認を行うか。
- 同じ操作を繰り返したとき、要求を無視するか、差し替えるか、並行して実行するか。
- 画面やサービスを閉じたとき、どの処理をキャンセルするか。
- 古い処理が遅れて完了したとき、その結果や後処理を状態に反映するか。

Tasking はタスクの所有、要求の受付、重複制御、キャンセル要求、終了待ちを担当する。
アプリケーションは表示状態、業務エラーの回復、結果の採用、副作用の順序を担当する。

## 処理の入口を選ぶ

| 処理の性質 | 選択 | 所有するもの |
|---|---|---|
| async 関数内で並行実行し、関数を戻る前に合流する | `async let` / task group | 関数のスコープが子タスクの終了を待つ |
| SwiftUI の表示期間や入力の変化に連動する | `.task` / `.task(id:)` | SwiftUI がタスクの寿命を管理する |
| 同期 UI コールバックから開始し、Action 単位で管理する | `ViewTaskStore` | Store が作成したタスクを所有する |
| async 呼び出しを重複制御し、型付きの終了結果を受け取る | `ActionRunner` | 呼び出し元がタスクを所有する |
| 非 UI サービスから差し替え可能な処理を開始する | `TaskSlot` | Slot が作成したタスクを所有する |

たとえば検索語に応じた読み込みには `.task(id: query)` が適する。
保存中の再クリックを拒否する同期ハンドラには Store の `.ignoreNew` を使える。
画面を閉じても同期を続ける場合は、アプリケーション側に Store を配置する。

## 3つの設計原則

### 所有と実行制御を分ける

Store と Slot はタスクを作成して所有する。Runner は呼び出し元のタスクで処理を実行する。
この責務配置により、キャンセル要求を出す先と、結果を受け取る方法が決まる。
Store と Runner は MainActor に隔離し、Slot は独立した actor とする。

### 受付・追跡・所有を別々の状態として扱う

受付は新しい処理を開始できるか、追跡は重複判定の対象か、所有は終了を管理すべきタスクがあるかを表す。
キャンセルは協調的であり、要求した時点で処理が止まるとは限らない。
Store はキャンセル時に追跡を解除するが、ハンドルは終了まで保持する。
終了確認には専用の完了待ち API を使う。

### 業務の判断をアプリケーションに置く

`ActionLifetime` はキャンセル対象を選ぶラベル、`CancellationContext` はキャンセルに協調する契約である。
ライフサイクルイベントとの接続、進捗やエラーの表示、再試行、古い結果の破棄は利用側が定義する。
これらを ViewModel やサービスの状態遷移としてテストする。

## 適用範囲

Tasking を使う機能では、所有者の配置、キャンセルへの協調、重複方針、終了処理を設計する。
実行が重なる場合は、結果と後処理に世代ガードを設ける。

処理の順序保証、同時実行数の制限、永続化、バックグラウンド実行は、それぞれの責務を持つ仕組みを使う。
たとえば副作用を順番に確定させるにはキュー、OS による中断を越えて転送するには対応する転送 API が必要になる。
大量の開始や照会は MainActor の時間を使うため、[性能特性](performance.md) の条件に沿って測定する。

Tasking はこの責務分担を学ぶためのリファレンス実装でもある。
MIT ライセンスの下で、ライブラリとして利用するほか、コードを読んで自分のアプリケーションに取り込める。
