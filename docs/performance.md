# 性能特性

Tasking の性能目標は、同期イベントから開始する処理の所有を少ない管理費用で明示し、
受付・キャンセル・実終了を混同せずに UI の実行時間と保持資源を管理できることである。
処理本体の計算やネットワークを高速化する機能は持たない。

## 計算量と保持

`n` は追跡中の実行数、`m` はキャンセル済みも含む所有中の未終了タスク数、
`k` は同じ ActionID の追跡数、`a` は未終了処理を持つ ActionID 数とする。
ハッシュ辞書の計算量は、衝突が偏らない場合の平均・償却値である。

| 操作・状態 | 計算量の目安 |
|---|---|
| ActionID / 個別実行の追跡照会 | 平均 O(1) |
| 未終了の総数・ID別件数・個別実行の照会 | 平均 O(1) |
| Store の開始、Runner の受付と終了 | 平均・償却 O(1)。Store はタスク作成の固定費を伴う |
| `cancel(id:)` | O(k) |
| グループの存在確認 | 最初の一致まで。最良 O(1)、最悪 O(n) |
| グループの件数照会・キャンセル対象選択 | O(n) |
| `cancelAll` / 解放時のキャンセル | O(m) |
| Store の追跡・所有・ID別未終了カウンターの空間 | O(n + m + a) |
| Runner の実行数カウンターの空間 | 未終了処理を持つ ActionID 数に比例 |

辞書の確保容量や疎密にも走査費用は影響される。
所有文脈が空なら自己待機の除外候補を走査しない。入れ子では、TaskLocal の継承された所有集合の構築と照合も伴う。
`waitForIdle()` の時間は処理本体と待機中の新規受付に依存し、固定時間では表せない。
ハンドルを順に await しても、既に開始している処理本体が逐次実行になるわけではない。

グループの追加索引は登録・キャンセル・終了で整合を保つ必要があるため、実負荷で走査が支配的と分かるまで持たない。
Runner は個別実行IDや二段辞書を作らず、ID別の件数だけを保持する。
所有識別子、追跡索引、自己待機の制約は [内部構造と不変条件](architecture.md#内部構造と不変条件) に定める。

## 評価する負荷

- 通常の UI 操作では、少数の開始と終了、キャンセルへの反応を確認する。
- `.cancelExisting` / Slot の `replace` では、前の処理が実終了するまで保持数が増え得る。
- 大量の開始・グループ照会・一括キャンセルは MainActor の同期時間として評価する。
- 重い同期計算は、サービスの actor や関数の隔離を確認し、UI 状態更新から分ける。

既定の `.ignoreNew` は、キャンセル済みも含む同じ ActionID の未終了処理がある間は新規受付を拒否する。
即時差し替えと並行実行は、同時実行数の制限ではない。入力段階のデバウンス・集約・受付制限を先に検討する。
終了まで保持する保証を外してメモリの見かけだけを減らしてはならない。

## 標準実装との比較

以下は ms 単位の「7プロセスの中央値〔最小〜最大〕」である。回数は各行のバッチ全体を表す。
タスク遅延の p95 は各バッチ内の測定値から求め、その値を7プロセスで集計する。

| 測定 | Tasking | 標準の手書き対照 |
|---|---:|---:|
| 128件の同期受付 | 0.268〔0.221〜0.288〕 | 0.075〔0.066〜0.081〕 |
| 10,000件の同期受付 | 17.766〔17.372〜19.613〕 | 5.659〔5.372〜5.889〕 |
| 128件の受付→開始 p95 | 0.254〔0.222〜0.287〕 | 0.101〔0.096〜0.112〕 |
| 10,000件の受付→開始 p95 | 17.246〔16.801〜18.970〕 | 6.811〔6.692〜7.530〕 |
| 128件のキャンセル→全終了 | 0.250〔0.229〜0.615〕 | 0.196〔0.146〜0.636〕 |
| 10,000件のキャンセル→全終了 | 18.048〔17.502〜19.704〕 | 12.152〔11.661〜13.225〕 |
| Runner 10,000回 | 3.342〔3.256〜3.995〕 | 1.632〔1.550〜1.820〕 |
| Slot 10,000回の差し替え | 10.275〔9.468〜11.571〕 | 7.876〔7.213〜8.256〕 |

対照は、同じ負荷で必要な受付・キャンセル・実終了までの所有を実装する。
単一の `Task?` を上書きしてキャンセル済みのハンドルを捨てる方式とは比較しない。
ただしグループ選択、複数 ActionID の管理、自己待機検出など API 全体の代替実装ではない。
Runner の対照は1操作の状態ガードであり、汎用の ID 別受付に払う追加費用も含めて読む。

単純な更新は通常の async と状態ガードで足り、複数の入口で ID 別の受付を共通化する必要がある場合に Runner を使う。
少数の所有でも追加費用はある。大量の同期受付にはばらつきがあり、中央値だけで UI の時間予算を満たすとは判断しない。
上記の10,000件の受付を一度の同期コールバックで行う用途には、入力の集約や構造化並行処理、件数制限を検討する。

### キャンセル後の保持と終了

`ownership` シナリオは全処理をゲートで止め、開始後にキャンセルする。
ゲートを開く前の `unfinished-after-cancel` は、全条件・全サンプルで入力件数と一致した。
キャンセル要求で処理が消えたとは扱わず、ゲート開放後に全件の処理本体と所有が終了したことを確認している。

キャンセル→全終了の時間にはゲートの即時開放とスケジューリングを含む。
実際の通信中断・キャンセルハンドラ・業務の後処理の応答時間は、この結果から判断できない。
長寿命所有者での定常的な開始と終了、異なるグループの混在、深い所有文脈は、利用アプリの負荷に合わせて追加測定する。

### MainActor の応答とメモリ

`uninterrupted-admission` は中断点のない受付バッチ、`main-actor-probe-delay` は直前に投入した
MainActor タスクの実行までの遅延である。描画やフレーム落ちの測定ではない。
計測のための時計と配列への記録は含み、区間中の JSON 出力は含まない。

プロセス全体の最大 RSS は中央値 45.88 MiB、範囲 45.84〜46.80 MiB だった。
同じプロセスが Tasking と標準対照の全シナリオを実行するため、実装別のメモリ差やリーク量には換算できない。
確保元や保持の解放を調べる場合は、実アプリで Allocations 等の観測と処理の実終了を組み合わせる。

## 再現と採用判断

[ベンチマークガイド](../Benchmarks/README.md) に、単独実行、独立プロセスの保存、同じ公開 API を持つソース間の比較、
プロファイリングと percentile の定義を定める。生の測定値は指定した結果ディレクトリへ保存する。

性能変更は、同じ処理・同じ終了保証で比較し、負荷条件とばらつきを報告する。
グループ索引、内部表現の公開、待機タスクの追加は、実際の支配的費用に利益があることを確認してから採用する。
性能の測定と公開契約の正しさの検証は別々に行い、CI の正しさテストには絶対時間のしきい値を置かない。
