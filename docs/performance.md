# 性能特性

Tasking のコストは、追跡中の実行数、ActionID の分布、終了待ちのタスク数に依存する。
Store と Runner の同期操作は MainActor の時間を使うため、1回の呼び出しと一括操作の両方を評価する。
この文書は計算量、測定した実装、結果の適用範囲を定義する。

## 計算量と保持するメモリ

`n` を追跡中の実行数、`m` を所有中のタスク数、`k` を同じ ActionID の追跡中の実行数とする。
ハッシュ辞書の操作は、衝突が偏らない場合の平均・償却計算量で表す。

| 操作・状態 | 計算量の目安 |
|---|---|
| ActionID / 個別の実行の照会 | 平均 O(1) |
| `start` / `.allowConcurrent` / Runner の登録・解除 | 平均・償却 O(1)。タスク作成などの固定費を伴う |
| `cancel(id:)` | O(k) |
| 寿命ラベルの存在確認 | 最初の一致まで。最良 O(1)、最悪 O(n) |
| 寿命ラベルの件数照会・対象選択 | O(n) |
| `cancelAll` / 解放時のキャンセル | O(m) |
| 所有文脈が空の場合の自己待機確認 | O(1) |
| 追跡索引と所有台帳の空間 | O(n + m) |

辞書の走査は確保容量や疎密にも影響される。
キャンセル済みでも処理が終了するまではハンドルと捕捉した依存を保持するため、`m` は `n` より大きくなり得る。
`waitForIdle()` の所要時間は処理本体の終了と待機中の新規受付にも依存し、固定時間では表せない。

## 設計上の選択

内部の所有識別子には独立した不変の参照を使い、寿命ラベルの存在確認は最初の一致で返す。
所有文脈が空の場合は、自己待機の除外候補を走査しない。
追跡情報は単一索引に置き、寿命ラベル用の追加索引の更新責任を持たせない。

存在確認は一致が早ければ安くなる一方、不一致では全件を走査する。
追加索引や内部実装のインライン化を検討する場合は、実アプリケーションの負荷で利益を確認する。
識別子の寿命と保守上の制約は [ADR-0015](adr/0015-measured-ownership-overhead.md) に定める。

## 測定対象と条件

[測定データ](performance-results.json) は、次の2つのソースを同じベンチマークで比較した記録である。
`working` と `baseline` は記録内のラベルであり、閲覧時のチェックアウトを表す名前ではない。

| 記録内のラベル | 所有識別子 | 寿命の存在確認 | 空の所有文脈での自己待機確認 |
|---|---|---|---|
| `working` | 保持された参照の一致 | 最初の一致で返す | 走査を省略する |
| `baseline` | UUID | 件数を数える | 候補を走査する |

どちらも追跡索引と所有台帳を分離する。
ソースはデータ内の `source_hashes` で識別し、Package.swift と Sources のコメントを含む内容が対象となる。
測定後に文書やソースを編集しても、記録したハッシュは変更しない。

| 条件 | 内容 |
|---|---|
| 測定日 | 2026-09-16（日本時間） |
| 環境 | Apple M1 Pro、16 GB、macOS 26.2、Swift 6.3.2 |
| ビルド | 独立した Release 実行ファイル。時間測定には Sanitizer とプロファイラを付けない |
| 集計 | 実行順を交互にした別プロセス7回の中央値。各シナリオのウォームアップ1回を除外 |
| 規模 | 100 / 1,000 / 10,000 実行 |
| ActionID | 1種類 / 最大100種類 / 実行ごとに異なる ID |

Store は全実行に `.screenBound` を使う。一致照会は `.screenBound`、不一致照会は `.appBound` を探す。
開始とキャンセルは処理本体が動く前に同期バッチで呼ぶ。終了待ちの時間には、
Swift のタスクスケジューリングと測定用ゲートも含む。
Slot の処理は、差し替えを受け付けている間にもゲートへ到達できる。

## 操作の所要時間

以下は `working` の記録で、各行は表に示す回数全体の中央値である。
Store は10,000実行・100 ActionID、Runner と Slot は10,000回の操作を対象にする。

| 操作 | 中央値 |
|---|---:|
| Store の開始 × 10,000 | 16.939 ms |
| Runner の実行 × 10,000 | 9.6825 ms |
| Slot の差し替え × 10,000 | 10.795 ms |
| 寿命の存在確認・一致あり × 1,000 | 0.034 ms |
| 寿命の存在確認・一致なし × 1,000 | 51.642 ms |
| 寿命の件数照会 × 1,000 | 17.422 ms |
| Store の寿命単位キャンセル、対象10,000実行 | 7.836 ms |
| Store の全実行の終了待ち | 17.671 ms |
| 一括処理後の完了待ち × 1,000 | 0.569 ms |
| `.ignoreNew` による重複拒否 × 1,000 | 0.167 ms |

100実行・100 ActionID の開始は合計約0.199 msである。
これらはランタイムと測定用の処理を含む実時間であり、Tasking 内部だけの CPU 時間ではない。

### アプリケーションへの適用

10,000回の同期開始は約17 msであり、一度に行うと描画へ影響し得る。
大量処理では task group や利用側の件数制限を検討する。
Store や Runner の処理本体に置いた同期計算も、MainActor の占有として評価する。

存在確認の一致ありは約0.034 ms、不一致は約51.642 msである。
不一致照会1回では約52 µsとなり、件数照会よりも遅い条件がある。
照会の一致率と ID の分布を実際の利用に合わせ、頻繁な全件走査が必要かを確認する。

### メモリ

`working` のプロセス全体の最大常駐メモリ（RSS）の中央値は43.75 MiB、範囲は43.59〜44.33 MiBである。
Swift ランタイムと測定用データを含む高水位の値であり、Tasking だけの使用中メモリやリーク量ではない。
保持が続く理由を調べる場合は、キャンセル要求だけでなく処理の実終了も確認する。

## 比較と補助観測

同じ7回比較による中央値を示す。

| 操作 | `baseline` | `working` |
|---|---:|---:|
| Store の開始 × 10,000 | 21.257 ms | 16.939 ms |
| Slot の差し替え × 10,000 | 19.969 ms | 10.795 ms |
| 寿命の存在確認・一致あり × 1,000 | 17.548 ms | 0.034 ms |
| 寿命の存在確認・一致なし × 1,000 | 33.510 ms | 51.642 ms |
| 一括処理後の完了待ち × 1,000 | 1.003 ms | 0.569 ms |
| プロセス全体の最大 RSS | 43.67 MiB | 43.75 MiB |

最大 RSS の範囲は `baseline` が42.75〜43.92 MiB、`working` が43.59〜44.33 MiBで重なるため、
この測定から明確なメモリ削減は判断できない。

Time Profiler の補助観測は1バッチの照会を1回にし、開始・キャンセル・完了を中心とした負荷を使う。
`UUID.init` を含む呼び出しの CPU サンプル比率は `baseline` 約8.2%、`working` 約4.6%である。
`OwnedTasks.keysExcludedFromWait` の走査は約2.7%と、サンプル未観測であった。
採録時間と反復数が異なるため、この比率を速度改善率には換算しない。
子呼び出しを含む比率には重複があり、足し合わせることもできない。

公開版0.3.0（コミット `4a3eeeedf37e291a7effeba08cad0cd24224d50c`）の別途5回の測定では、
同じ10,000実行・100 ActionID の開始が約14.81 ms、寿命の件数照会1,000回が約857 ms、
Slot の10,000回差し替えが約10.2 msであった。7回比較とは測定系列が異なるため、小差から優劣を断定しない。
`@inlinable` / `@usableFromInline` の別途11回比較でも、明確な利益は確認されていない。

## 自分の負荷で測る

実行・比較・プロファイルの手順は [ベンチマークガイド](../Benchmarks/README.md) に示す。
利用者の端末、実行件数、ID 分布、照会の一致率、キャンセル後の未終了タスク数に合わせて測る。
測定条件とばらつきを結果に添え、性能の測定と公開契約の正しさの検証を分ける。
